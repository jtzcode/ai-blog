# 理解模块化
在现代软件系统的设计中，模块化（Modularization）方法可谓一种共识或者最佳实践。事实上，早在 1971 年模块化已经是软件工程中的共识。计算机科学家 David Lorge Parnas 在他的经典文章 *On the Criteria to Be Used in Decomposing Systems into Modules* 中讨论了模块化设计的原则。在文章开头他甚至调侃，「如果程序员会唱赞美诗，那么“模块化程序设计”一定是最流行的赞美对象之一。」

【这里放一张Parnas的照片】

然而，当时那些最典型的大型软件失败案例，本身往往已经是**形式上**高度模块化的系统。所以问题的关键并不在于系统有没有被拆成若干模块，而是**依据什么标准**，把系统拆成这些模块。

Parnas 认为，模块化能带来三种重要收益：

* 不同团队能够相对独立地开发；
* 一个局部变化尽量不影响其他部分；
* 调用者可以一次理解一个模块，而不用理解整个系统。

这三点如今看起来已不新鲜，但这是几十年前的观点，那时面向对象的编程语言还屈指可数。况且，这三点只是收益和结果，而非手段和方法。只有正确的模块划分，才能真正得到这些收益。

这里可以用一句话概括模块划分的思路：

> 有利于管理知识、变化和依赖在系统中的传播。

## 抽象与信息隐藏

讨论模块化，就绕不开两个常见的概念：抽象（Abstraction）与信息隐藏（Information Hiding）。我认为这两个概念的含义更宽泛，是设计思想而不是具体技术。

简单而言，抽象决定我们**用什么概念**理解系统，而信息隐藏决定我们**不应该知道什么**。

如果你熟悉面向对象编程语言，那么使用这类语言本身进行程序设计，就是抽象和信息隐藏的具体实践。在架构和流程图上，我们看到的是一个一个类之间的关系，以及用于交互的接口定义，而不是类的内部实现细节。在不知晓这些细节的情况下，不但没有影响我们对系统的理解，反而让这种理解在面对复杂系统时更为简洁清晰。

模块拆分做的好不好，就取决于抽象和信息隐藏的质量。系统的复杂性不仅取决于模块的多少，更取决于模块之间的**依赖关系**。抽象和信息隐藏本质上是在控制模块之间的依赖。依赖无法消除，但是可以**精简**。

一个模块可以是一个类、一个文件或一个函数。但 Parnas 特别提醒：

> module 最好理解为一个 *work assignment unit*，而不是一个 subprogram。

可以这样理解，`subprogram` 依旧是以功能视角看待系统，每个子程序可以各自完成任务，但是可能彼此依赖。
一个模块真正表达的是：

> **关于系统的一组设计决策，应该由谁负责，其他部分需要知道多少。**

所以判断系统有没有良好的模块化，不能简单看：

* 文件是不是拆得足够小；
* 类是不是足够多；
* package 是不是足够整齐。

真正应该看的是：

> 修改一个设计决策时，究竟有多少地方必须跟着知道和修改。



抽象解决的是“我们看到什么”。

例如调用：

`line.word(i, j)`

调用者面对的是“第 i 行第 j 个单词”。

它不需要面对：

* 字符如何压缩；
* 数据存在哪里；
* 有没有索引；
* 数据是否全部驻留内存。

这些实现细节从调用者的思维模型中消失了。

信息隐藏：决定我们不应该知道什么

Parnas 的信息隐藏思想更进一步。

他提出：

> 每个模块都应该围绕一个重要的设计决策建立，并把这个设计决策隐藏起来。

所以模块边界实际上也是**知识边界**。

---

AI 降低了生成代码的成本，也让软件能够以更高的频率发生变化。这使模块化、信息隐藏和接口设计获得了更直接的价值：每次增加功能、修复缺陷或替换实现时，我们都需要知道，修改会影响哪些地方，哪些既有性质必须继续成立。代码可以迅速生成，这些关系仍然需要被理解和维护。**生成速度越快，控制变化范围就越重要。**

Parnas 在《On the Criteria To Be Used in Decomposing Systems into Modules》中提出，应当围绕难以确定、或者可能变化的设计决策划分模块，让每个模块隐藏其中的一项决策。这种划分能够减少协同所需的信息，使系统可以逐个模块地被理解，也让一部分实现发生变化时，其他部分保持稳定。这些收益同样适用于参与开发的 AI：清晰的边界为它提供了局部工作的条件。

相关研究已经提供了一些实证支持。发表于 ICLR 2024 的 CodeChain，将任务分解、子模块复用与迭代修订结合起来。在 APPS 基准上，采用 GPT-3.5 的方案将 pass@1 从 22.33% 提高到 30.24%，相对提升约 35%。不过，论文的消融实验还发现，单独使用引导模块化的提示，可能降低直接生成的正确率；收益需要与后续的筛选、复用和修订配合。这说明，模块划分能够为验证和改进创造条件，但“多写几个函数”本身并不保证质量。这项研究主要考察编程题中的函数级分解，对大型系统中信息隐藏的长期收益，还需要其他证据补充。[Le 等，*CodeChain*，2024](https://arxiv.org/abs/2310.08992)

AI 能够生成模块的外观，也可能在实现中破坏模块的边界。2025 年的探索性论文《The Modular Imperative》记录了一个很具体的例子：研究者要求模型为 Todo 应用增加统计模块，模型创建了独立文件，却直接访问存储模块的私有成员，使统计功能依赖于内部实现。文件已经分开，设计决策仍然泄漏到了外部。这项小规模研究提醒我们，代码审查必须追问每个模块究竟依赖了什么。[Kravchuk-Kirilyuk 等，*The Modular Imperative*，2025](https://namin.seas.harvard.edu/pubs/lmpl-modularity.pdf)

功能测试也未必能发现这种退化。2026 年的 NITR 预印本，在 21 个小型 C++ 仓库案例上评估了 23 种编码配置：483 个结果中，有 64 个通过了全部功能测试，却未通过针对可维护性的结构检查。这些经过专门设计的案例不能直接代表所有生产项目，但它们清楚地揭示了一个缺口：满足当前行为要求的修改，仍可能增加下一次修改的困难。[Zhu 等，*Needle in the Repo*，2026](https://arxiv.org/abs/2603.27745)

我的看法是，**模块边界同时也在界定一次修改需要理解的范围。**例如，一个订单系统接入新的支付渠道，如果渠道 SDK、签名规则和错误码散落在订单、退款与对账代码中，AI 就必须追踪这些隐含联系。把渠道差异封装在支付模块内，并提供稳定的业务接口，可以让相当一部分修改集中在明确的范围中。不过，接口必须公开调用方需要知道的语义：超时可能意味着支付结果未知，重试需要满足幂等要求。只有这些约定足够准确，调用方才有依据忽略内部实现。信息隐藏的价值，正来自这种有依据的信息省略。

这种省略也具有计算上的意义。Bai 等人在 2026 年分析了八种模型通过 OpenHands 执行 SWE-bench Verified 任务的轨迹，发现输入上下文是 token 消耗和成本的重要来源，重复读取与持续累积的上下文尤其值得关注。[Bai 等，*How Do AI Agents Spend Your Money?*，2026](https://arxiv.org/abs/2604.22750) 据此可以提出一个工程推断：如果良好的设计减少了完成修改所必需的上下文，就有机会减少探索、重复阅读和返工。不过，这篇论文没有通过模块化重构的对照实验直接证明节省比例；具体收益仍需在项目中测量。

因此，工程师使用 AI 时，应当把设计要求落实到工作流程中。开始生成代码之前，先明确状态由谁管理、哪些实现可能变化、哪些依赖被允许，以及接口需要保证哪些性质。把这些决定写进简短的规格说明、类型定义和契约测试，能够让 AI 获得具体的判断依据。分配任务时，提供相关实现、接口约定和测试，使它具备完成局部修改所需的信息；涉及公共契约变化时，再系统检查调用方和跨模块影响。

交付时，除了检查功能是否实现，还应检查新增依赖、状态访问和职责归属。适合自动检查的规则，例如禁止循环依赖、限制跨层导入、禁止访问其他模块的内部实现，可以交给静态分析和持续集成执行。涉及业务含义和边界取舍的判断，则需要工程师认真审查。模块也应随着需求演进而调整：如果一个小改动总要穿过许多层接口，或者多个模块总是一起修改，就值得重新审视原来的划分。

AI 让实现变得便宜，好的设计让下一次改变也能保持便宜。工程师需要持续关注的，正是每次交付之后，系统还保留了多少被理解、被验证和被改变的余地。

模块化还可能直接影响 AI 编程的使用成本。一个编码 agent 完成任务时，需要不断搜索代码、读取文件、分析依赖、修改实现，再根据测试结果继续调整。每轮交互都要处理相应的上下文。因此，一次修改的 token 消耗，同时受到每轮处理的信息量和完成任务所需轮数的影响。模块设计能够作用于这两个环节：明确的职责帮助它定位相关代码，稳定的接口减少需要追踪的实现细节，局部可验证的修改则有机会减少反复修补。

对 token 消耗的研究说明了这一问题的分量。Bai 等人分析了八种模型通过 OpenHands 执行 SWE-bench Verified 任务的轨迹，发现输入上下文在总体 token 消耗中占据主导地位；进一步针对 Claude Sonnet 4.5 的成本分析还发现，即使启用了缓存，累积上下文的重复读取仍然是主要费用来源。这意味着，最终提交几十行代码的任务，可能已经在此前的探索过程中处理了大量信息。代码生成量很小，完成修改所需的信息处理量却可能很大。[Bai 等，*How Do AI Agents Spend Your Money?*，2026](https://arxiv.org/abs/2604.22750)

也有研究直接考察代码质量与推理消耗之间的关系。Hu 等人的 Token-Aware Coding Flow 研究，使用 DeepSeek-R1 比较存在代码异味的 Java 样本及其重构版本，报告消除长函数、重复逻辑等问题后，相关 token 指标有所下降。不过，这项探索性研究使用了时间或复杂度归一化的指标，功能一致性也主要通过代码和文档相似性衡量。因此，它提供了代码结构可能影响推理开销的初步证据，文中常被引用的“约 50%”不宜直接解释为实际任务的 API 费用减少一半。[Hu 等，*Optimizing Token Consumption in LLMs*，2025](https://arxiv.org/html/2504.15989v2)

仓库级研究则进一步揭示了结构信息的价值。发表于 NeurIPS 2025 的 RepoMaster，通过层次化仓库分析、按任务探索代码和筛选相关信息，帮助 agent 使用已有代码。在保持基础模型不变的消融实验中，移除层次化仓库分析后，token 消耗增加约 9.7%。这支持了一个具体判断：让 agent 更容易掌握代码结构，可以减少探索开销。不过，该实验改变的是 agent 理解和导航仓库的方式，不能把这个比例直接当作代码模块化重构的收益。[*RepoMaster*，NeurIPS 2025](https://papers.nips.cc/paper_files/paper/2025/file/98da9cdb7e8af9192f1fe2cb38690d60-Paper-Conference.pdf)

基于这些结果，我认为，模块化具有一种值得重视的经济价值：**它有机会减少完成一次正确修改所必需的信息量。**仍以支付系统为例，如果修改签名算法需要同时阅读订单状态机、退款流程和对账逻辑，相关设计决策就已经跨越了多个边界。把签名规则封装在支付渠道适配模块中，并建立准确的接口契约，能够让修改者集中处理算法及其测试。整个项目的代码量可能没有减少，但这项任务需要处理的代码范围缩小了。

这里还需要区分两个相互配合的工作：模块设计减少实际存在的依赖，上下文组织帮助 agent 找到并理解这些依赖。架构文档、目录说明和依赖图能够改善导航；当业务规则确实散落在多个模块中时，理解这些联系仍然需要付出成本。反过来，即使代码划分合理，如果工具每次都把整个仓库放进上下文，局部理解的优势也难以充分体现。**设计提供了少读代码的条件，工具和工作流程决定能否利用这个条件。**

这也解释了为什么模块数量增加，有时会让 token 消耗上升。层层转发的接口、含义模糊的抽象、分散的状态，以及必须同时修改的多个小文件，都可能迫使 agent 进行更多跳转和核对。判断模块化是否有效，可以观察一个具体事实：完成某项业务修改时，需要同时理解多少信息、协调多少关系？文件数量和单个文件的行数只能提供局部线索。

对工程师而言，可以优先关注那些修改频繁、每次都需要大范围阅读和反复修补的区域。把容易变化的决策收拢到明确的模块中，补足接口语义和局部测试，再让 agent 按任务读取相关内容。评估效果时，应在相同模型、工具和可比任务下，记录输入、输出及缓存 token、交互轮数、任务成功率和人工返工情况，以通过验证的修改成本衡量收益。一次交互更短，只有在完成质量得到保持时才有意义。

由此还可以进一步推断：随着 AI 参与修改的频率上升，代码结构的影响会被反复兑现。一个隐藏依赖可能在每次任务中引发重新搜索、重新理解和重新验证；一次有效的边界调整，则可能持续减少这些重复工作。技术债由此多了一种可观察的支出形式——每次维护，都可能为同一份结构复杂性再次消耗 token。
